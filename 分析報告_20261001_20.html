1. 專案概觀

簡易 ERC20 錢包服務,採 MVC 分層(controller → service → dao)。對外提供 4 支 HTTP API,另有 2 支背景排程(啟動時由 service.RunCron() 註冊),負責掃描鏈上區塊與確認交易。資料表:address、tokens、block_height、transaction、withdraw。

2. HTTP API 清單(前綴 /v1)

#方法路徑Controller用途主要參數流程摘要

3. 背景排程(每 5 分鐘)

排程函式用途狀態
監聽區塊RunListenBlock比對 DB 高度與鏈上最新高度,逐塊掃描 ETH 轉帳與 ERC20 Transfer 事件,僅保留與本服務地址有關的交易(判斷充幣/提幣)寫入 transaction,高度 +1。遞迴追到最新;DelayIfStillRunning 避免重疊啟用
確認交易RunTransactionConfirm取待確認且區塊高度 ≤ 最新高度 − 12 的交易(最多 20 筆),取 receipt 設成功/失敗、手續費、確認數,並標記待通知啟用
通知商戶RunTransactionNotify將完成的交易通知商戶 URL已註解停用

4. 問題與風險

🔴 高:安全性

  1. 1. 私鑰外洩風險:POST /v1/address 直接回傳私鑰、DB 不存私鑰;/withdraw 要求 Body 帶 secret_key,明文傳遞,且 sendTransactionByETH/ByToken 會 logs.Debugf("req:%+v") 把含私鑰的整個請求寫進日誌。
  2. 2. 設定檔機密進版控:config.yaml 含 Infura Key(Sepolia 與 mainnet)、DB 帳密(root/1234)、JWT 金鑰,請視為已洩漏並重新核發。編譯產物 webapi_erc20.exe 也在專案中。
  3. 3. 所有 API 無認證/授權:設定檔有 auth 區塊但路由未掛任何中介層,任何人皆可提幣、建地址。
  4. 4. 未驗證金鑰與地址匹配:未檢查 secret_key 與 from_address 是否對應,也未檢查地址是否為本服務產生、商戶是否擁有。
  5. 5. 主網/測試網混用:redis.url 放 Sepolia 節點、node_bk.url 放 mainnet,欄位命名混亂,易誤送主網。

🟠 中:正確性與一致性

  1. 6. DB 交易未生效:createTransAndUpdateBlockHeight 先 SqlSession.Begin(),但寫入使用全域 SqlSession 的 repository,並不在該交易內,Rollback 無作用,可能出現交易已寫入但高度未前進而重複掃描。
  2. 7. 先上鏈後寫 DB、無冪等:寫 DB 失敗時鏈上已送出但 API 回錯誤,呼叫端重送會重複轉帳。
  3. 8. Nonce 競態:使用 PendingNonceAt,同地址併發提幣會取到相同 nonce。
  4. 9. 錯誤被吞掉:runListenBlock 任何錯誤僅 Debugf 後 return;壞區塊整塊跳過,無告警。
  5. 10. getETHFromAddr 無 default:未知交易類型回傳零地址,chainID 檢查被註解掉。
  6. 11. 確認流程脆弱:單筆錯誤即整批中止;只看區塊高度差 ≥ 12,未處理 reorg。
  7. 12. 遞迴掃描:runListenBlock() 遞迴,落後很多時可能深層遞迴,應改迴圈;<= 判斷會多打一次節點。
  8. 13. 節點連線問題:Dial 失敗直接返回不試下一個節點;全部 ping 失敗仍回傳 client 且 err 為 nil;每次新建連線且從不 Close,造成連線洩漏。
  9. 14. 輸入驗證不足:amount 未檢查為正數與精度;txHash 未驗格式。
  10. 15. 回應碼語意不當:所有失敗回 400;ShouldBindJSON 失敗回 CodeInternalError。
  11. 16. 缺少索引/唯一鍵:wallet_eth.sql 除主鍵外無索引(tx_hash、address、status+block_height、notify_status),tx_hash 無唯一約束(若靠 gorm tag 建立請確認實際表結構)。

🟡 低:效能與可維護性

  1. 17. N+1 查詢:每筆 Value>0 交易做 2 次 GetByAddress + 1 次 isNewTransaction;每個 Transfer log 單獨 GetTransactionByHash。
  2. 18. 重複查詢與解析:每塊重查兩次 token 清單,每次 getAmount 重新解析 ABI。
  3. 19. 日誌問題:多數錯誤用 Debugf,正式環境看不到;dao.ConnectUrl 會印出含密碼的 DB URL。
  4. 20. 程式整潔:大量註解舊碼、transaction_service.go 單檔 830 行、可用 strings.Contains。
  5. 21. 測試不足:僅 address_test.go、reflect_test.go,核心流程無測試。
  6. 22. 連線池:SetMaxOpenConns(300) 對單機 MySQL 偏大。
  7. 23. Gin 設定:gin.Default() + debug 模式,缺 release、request-id、限流、超時、graceful shutdown。

5. 優化建議(建議執行順序)

第一階段:先處理安全(立即)

  1. 撤銷並重新核發 Infura Key、更換 DB 密碼;機密改用環境變數或 Secret 管理,config.yaml 只留範本並加入 .gitignore,同時從 git 歷史清除。
  2. 移除 webapi_erc20.exe 與 log/ 的版控。
  3. 所有路由加認證(JWT 或 API Key + HMAC)與商戶授權;/withdraw 加 IP 白名單與限流。
  4. 私鑰改由伺服器端加密保管(KMS/HSM 或至少 AES 加密入庫),提幣只傳 from_address,由服務端簽章;建立地址不回傳私鑰。若維持現行設計,至少全程 HTTPS 並遮罩日誌。
  5. 日誌遮罩敏感欄位(私鑰、密碼、含密 URL)。

第二階段:資金正確性

  1. 修正 DB 交易:repository 接受 *gorm.DB 或使用 SqlSession.Transaction(...),讓寫入交易與更新區塊高度在同一 transaction。
  2. 提幣冪等與狀態機:先寫 withdraw(pending、唯一 request_id)→ 簽章廣播 → 更新 tx_hash/狀態。
  3. Nonce 管理:每地址互斥鎖或自維護 nonce 表,支援卡單加價重送。
  4. tx_hash 加唯一索引;補 address.address、transaction(status, block_height)、transaction(notify_status)、withdraw.tx_hash 索引。
  5. 確認邏輯:單筆失敗 continue 並記錄;確認前驗證區塊 hash 仍在主鏈以處理 reorg。

第三階段:穩定性與效能

  1. 共用單一 ethclient(可重連、多節點 failover、結束 Close)。
  2. 掃描改迴圈 + 批次:收集區塊內所有地址以 IN (...) 查詢,或將「我方地址」載入記憶體集合;ERC20 用 FilterLogs 一次抓區間事件。
  3. token 清單與 ABI 解析結果做快取。
  4. 考慮以 WebSocket SubscribeNewHead 取代 5 分鐘輪詢;確認 12 個區塊約 2.5 分鐘,5 分鐘輪詢會讓延遲再加倍。
  5. 啟用 RunTransactionNotify 前補上重試、退避、簽章與冪等,並與確認流程解耦。

第四階段:程式品質

  1. 統一回應碼:400 / 401 / 404 / 500 / 502 語意分明。
  2. 強化驗證:金額 > 0 與精度、EIP-55 checksum 地址(common.IsHexAddress)、txHash 格式。
  3. 拆分 transaction_service.go(scanner / confirmer / notifier),刪除註解舊碼。
  4. 補單元與整合測試(Sepolia 或 simulated backend)。
  5. 正式環境:gin.SetMode(release)、graceful shutdown、/healthz、Prometheus metrics、告警(區塊落後數、待確認筆數、節點失敗率)。
  6. 加入 Dockerfile 與 CI(go vet、staticcheck、gosec、go test)。

6. 風險總結

面向評級說明
安全性高無認證、私鑰明文傳輸且可能入日誌、機密進版控
資金正確性中高無冪等、nonce 競態、DB 交易未生效
穩定性中連線洩漏、單點節點、錯誤吞掉
效能中低逐筆查 DB、輪詢延遲
可維護性中低單檔過大、測試少

本報告基於靜態閱讀程式碼,未實際執行;common/ethereum/transaction.go(gas 估算、簽章細節)與各 repository 僅做重點檢視,建議高風險項目修正後再做一次深入檢視。
